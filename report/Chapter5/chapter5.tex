\section*{Introduction}
% intent: Frame this chapter as the result rather than the mechanism: the
% platform as its users and operators actually meet it, walked screen by
% screen on the pilot's demo tenant, closing with the measurements the running
% system produced. Per the report-wide rule, the chapter intro must not
% reference other chapters.
A platform is judged on what it puts in front of the people who use it.
This chapter walks the delivered CLMPilot platform as they meet it, on
the pilot running in production at \url{https://clmpilot.com}. 

%--------------------------------------------------------------------
\section{Access and onboarding}
\label{sec:walk-access}
% intent: Open the walkthrough where a user opens the product: the two-step
% sign-in. Show the result of the authentication journey without repeating its
% mechanism.

A user reaches CLMPilot at a single address and signs in through 2
steps: the credentials first, then a one-time code delivered by email.
Figure~\ref{fig:ui-login-otp} shows the second of them. Only once the
code is confirmed does the session begin, and it is renewed quietly
before it expires, so a working day never ends in an unexpected
sign-out.

\uishot[Two-step sign-in]{ui-login-otp}
  {the sign-in page at the second step, where the emailed one-time code
   is entered.}
  {Two-step sign-in: the one-time-code confirmation that completes
   authentication.}

A new colleague arrives by invitation instead. The invitation mail is
written in the language chosen by the person who sent it, and the page
it opens asks for an explicit click before anything is consumed, so a
corporate mail scanner cannot burn the single-use token on the
recipient's behalf. Accepting it costs the new user exactly one code:
registration and first sign-in complete together, and the user lands
inside the tenant already authenticated
(Section~\ref{sec:iam-practice}).

\section{The contract registry and its audit trail}
\label{sec:walk-registry}
% intent: The core of the product as the user sees it -- the filterable
% registry and the per-contract event history.

The registry is where the working day starts.
Figure~\ref{fig:ui-contract-list} shows it as the demo tenant's users
see it: every contract of the organisation in one filterable listing,
with a free-text search across the descriptive fields and filters on
department, category, status and counterparty. Opening a record gives
the business metadata, the status, the linked document, the deadlines
derived from it and the people involved.

\uishot[The contract registry]{ui-contract-list}
  {the contract registry with the filter bar and the free-text search
   active (e.g.\ filtered to one department).}
  {The contract registry: filterable listing backed by the
   case-insensitive search projection of
   Section~\ref{sec:backend-comby}.}

Every record carries its own history, and the platform shows it without
interpretation. Figure~\ref{fig:ui-audit-trail} shows the audit-log tab
of a contract: each entry names the actor, the moment and what changed.
Nothing in the interface can remove an entry, because nothing in the
platform can; a deletion is recorded as one more event
(Section~\ref{sec:contract-domain}). The same history is available as an
exportable file for an auditor who needs it outside the application, and
it is served only to a user who may already read the contract itself.

\uishot[The audit-log view of a contract]{ui-audit-trail}
  {a contract's audit-log tab showing the event list with actor,
   timestamp and payload of each entry.}
  {The audit-log view of a contract: the raw event stream rendered
   with actor, timestamp and payload.}

\section{Fitting the platform to the organisation}
\label{sec:walk-config}
% intent: What a tenant administrator configures -- custom fields and the
% document-provider connections. Both are the visible half of Phase-2 work.

No 2 legal departments track the same attributes, so the contract form
is only partly fixed. A tenant administrator defines the fields that
matter to the organisation, choosing a type for each, and the form grows
accordingly: Figure~\ref{fig:ui-contract-form-custom-fields} shows the
fixed fields followed by the tenant's own, one widget per definition,
with the date pickers, numeric inputs and selection lists that each type
implies. The rules an administrator sets are applied when the contract
is saved, not merely suggested in the browser
(Section~\ref{sec:contract-domain}).

\uishot[The contract form with custom fields]{ui-contract-form-custom-fields}
  {the contract form of the demo tenant, scrolled to the
   tenant-defined custom fields so the data-driven widgets are
   visible.}
  {The contract form: fixed fields followed by the tenant's typed
   custom fields, one widget per definition.}

The second piece of configuration connects the organisation's own
document storage. Figure~\ref{fig:ui-settings-integrations} shows the
integrations area, where an administrator authorises CLMPilot against
Google~Drive or SharePoint once and for the whole tenant. What the
connection grants is deliberately narrow: the platform links to
documents and reads them when asked, and never takes a copy into its own
storage. Users afterwards pick a file through the provider's own picker
and see it appear on the contract as a link.

\uishot[The integrations settings of a tenant]{ui-settings-integrations}
  {the Settings page, Integrations tab, with the Google Drive card in
   the Connected state.}
  {The integrations settings of a tenant administrator: the per-tenant
   OAuth connections behind the \texttt{DocumentStore} adapters.}

\section{Approvals, deadlines and obligations}
\label{sec:walk-workflow}
% intent: The three time/workflow contexts as the user experiences them: an
% inbox, a horizon of dates, a list of owned tasks.

A contract that needs review before it takes effect carries an approval
chain, and each approver meets it as an inbox.
Figure~\ref{fig:ui-approval-inbox} shows that inbox: the steps waiting
on this user, in the order the chain defines. An approver acts only on
their own step, and a single rejection ends the chain for everybody. When
the last approver signs off, the contract becomes active without anyone
having to remember to activate it.

\uishot[The approval inbox]{ui-approval-inbox}
  {the approval inbox of a user with at least one pending step; one
   workflow expanded to show the ordered steps.}
  {The approval inbox: ordered steps, each awaiting its designated
   approver.}

Deadlines are the part of the product that works while nobody is
watching. Registering a contract is enough to create them: the expiry,
the cancellation window computed back from the notice period, and the
renewal date when the contract renews itself, each with reminders at 90,
60 and 30 days. Figure~\ref{fig:ui-deadline-timeline} shows the result:
the horizon of what is coming, with the reminders that will announce it.
A deadline a user has edited is left alone by the automation
(Section~\ref{sec:workflow-temporal}), and reminder mail is sent only to
users who asked for it.

\uishot[The deadline view]{ui-deadline-timeline}
  {the deadline view with upcoming deadlines and reminder markers (90,
   60, 30 days) visible.}
  {The deadline view: automation-created markers with their reminder
   horizon.}

Obligations answer a different question: not what date is approaching,
but what somebody has to do. Figure~\ref{fig:ui-obligations} shows one
recurring commitment with its occurrences. A user creates the
obligation, owns it and completes it; completing a recurring one makes
the next occurrence appear straight away, on the calendar day the
original set, and never in the past. The reminders sit closer, at 14, 7
and 1 days, because operational tasks have shorter warning than contract
dates.

\uishot[Obligation tracking]{ui-obligations}
  {the obligation view with a recurring obligation and its
   completed/upcoming occurrences.}
  {Obligation tracking: person-owned recurring tasks with the shorter
   14/7/1-day reminder horizon.}

\section{Reading and signing the document}
\label{sec:walk-intel}
% intent: The two Phase-2 enterprise subsystems as a user meets them: the
% enrichment review UX and the signature panel.

Linking a document changes what the record knows about itself. Within a
few seconds of the link, the platform has read the document and proposes
what it found: the counterparty, the dates, the value, the contract type
and the clauses it could quote.
Figure~\ref{fig:ui-enrichment-review} shows those suggestions on a
contract overview. The review is field by field --- accept, edit or undo
--- and nothing a person typed is ever overwritten, because only empty
fields are proposed for filling (Section~\ref{sec:intel-esign}). A
suggestion the user rejects leaves no trace on the record.

\uishot[Enrichment suggestions on a contract]{ui-enrichment-review}
  {a contract overview right after linking a document, with the
   intelligence suggestions shown per field and the accept / edit /
   undo controls visible.}
  {Enrichment suggestions on a contract of the demo tenant, reviewed
   field by field (accept, edit or undo); only fields the user left
   empty are filled.}

The same document can be sent for signature without leaving the
contract. Figure~\ref{fig:ui-esign-status} shows the signature panel of
a request in progress: the signers in the order they will be asked, and
where each one stands. The panel updates itself as the provider reports
progress; nobody has to refresh a status by hand. When the last signer
finishes, the executed document comes back and attaches itself to the
contract as an ordinary link, so it enters the same audit trail as
everything else, and a contract still in draft becomes active on the
spot.

\uishot[The signature request on a contract]{ui-esign-status}
  {a contract's signature panel with a request in progress (signers
   and their statuses), against the DocuSeal sandbox.}
  {The signature request on a contract: ordered signers and per-signer
   status, updated by the webhook return path.}

\section{Reporting and the dashboard}
\label{sec:walk-reporting}
% intent: The self-service reporting surface and the landing dashboard --
% where all the automation becomes visible at portfolio level.

Above the individual contract, the platform reports on the portfolio.
Figure~\ref{fig:ui-report-builder} shows the report builder: the user
chooses the columns, the grouping and the chart, sees the result
immediately, saves the configuration under their own name and, if the
report is one they need regularly, schedules it as a recurring export
delivered by email. The available measures include portfolio value,
per-department and per-counterparty rollups, and a risk score whose
contributing factors --- value, expiry proximity, missing documents ---
stay visible, so a reviewer can always see why a contract scored as it
did.

\uishot[The report builder]{ui-report-builder}
  {the report builder with columns, a grouping and a chart type
   selected, and the rendered chart visible.}
  {The report builder on the demo tenant: self-service columns,
   groupings and chart over the reporting projections.}

The dashboard is where a user lands after signing in, and it is the
clearest view of what the automation has been doing.
Figure~\ref{fig:ui-dashboard} shows it: the portfolio indicators, the
contracts approaching expiry and the deadlines coming up. None of it is
compiled by hand; every tile is a query over the read models the
platform maintains as events arrive (Section~\ref{sec:backend-comby}).

\uishot[The dashboard]{ui-dashboard}
  {the dashboard after login: KPI tiles, the expiring-contracts list
   and the deadline overview.}
  {The dashboard, with the expiring-contracts view served by the

\section{The product in 2 languages}
\label{sec:walk-i18n}
% intent: Internationalisation as a delivered property, shown through the
% bundled help area -- the one screen that proves the docs ship with the code.

The platform is delivered in English and German, and the choice follows
the user rather than the browser: it is stored on the identity, so it
holds across devices, and it travels with the notifications the platform
sends, so each recipient reads their own language. Dates, numbers and
currencies follow the same locale, including the day-first date ordering
the European users of the English interface expect.

The user documentation is delivered the same way. It is not a separate
site to be kept in step but a help area inside the application, built
from the documentation sources at the same time as the code and shipped
in both languages. Figure~\ref{fig:ui-help-de} shows it in German. A
user who upgrades therefore never reads documentation for a version they
are not running.

\uishot[The bundled help area in German]{ui-help-de}
  {the in-app help area in the German locale, to show the bundled
   bilingual documentation.}
  {The bundled help area in German: documentation versioned and
   shipped with the code it describes.}

\section{The platform from the operator's side}
\label{sec:walk-admin}
% intent: The cross-tenant administration area -- the one surface that is not
% part of any customer tenant.

One surface of the platform belongs to nobody's tenant.
Figure~\ref{fig:ui-admin-tenants} shows the cross-tenant administration
area, reachable only by the platform's own operators: the provisioned
organisations, the action that creates a new one, and the archival that
ends a subscription. Provisioning a tenant from here creates the
organisation, waits for its role groups to be in place and sends the
first administrator their invitation, after which the customer
administers themselves. Archiving is not a deletion --- the tenant's
history stays intact and its users meet an explicit end-of-service
screen (Section~\ref{sec:iam-practice}).

\section{One contract, end to end}
\label{sec:walk-scenario}
% intent: Tie the preceding sections into a single narrative so the chapter
% reads as a product, not a catalogue of screens.

The screens above meet in a single working sequence. A legal manager
registers a contract on the form of
Figure~\ref{fig:ui-contract-form-custom-fields}, where the fixed fields
are followed by the ones their organisation defined. They link the
signed document from the company's own Drive through the connection of
Figure~\ref{fig:ui-settings-integrations}; the link returns within a
second, and a few seconds later the suggestions of
Figure~\ref{fig:ui-enrichment-review} are on the record. The manager
accepts the extracted dates and corrects the counterparty.

Nothing else has to be done by hand. The accepted dates have already
created the deadlines of Figure~\ref{fig:ui-deadline-timeline}, with
their reminders scheduled. The contract has appeared in the registry of
Figure~\ref{fig:ui-contract-list} and in the expiring-contracts view of
the dashboard of Figure~\ref{fig:ui-dashboard}. And the audit tab of
Figure~\ref{fig:ui-audit-trail} already carries every one of those
steps, in order, with the actor behind each. What took a manager a
morning of spreadsheet work and calendar entries in the situation the
project set out to address is, here, one form and one review.

\section{Measured performance in production}
\label{sec:runtime-perf}
% intent: Close the chapter with evidence. The framework's in-process
% instrumentation at the dispatch chokepoint; the embedded operator dashboard
% (figure), deliberately off the public surface; then the analysis of one
% production window -- traffic mix dominated by the temporal automation,
% read-path costs orders of magnitude inside the Ch II budgets, external
% round-trips absorbed on the async event path, sub-ms dispatch overhead,
% zero internal failures, every rejection a rule holding. Numbers were read
% off the pilot's runtime table on 2026-08-05 (~8 days after the last stack
% restart); counters accumulate since process start, so a later capture
% shows the same shape at larger counts.

The chapter closes with measurements from the running pilot. Since
every command, query and event goes through the same dispatch point,
the framework can count them all: how many succeeded, failed or were
rejected, how many arrive per second, and for each message type the
shortest, average and longest handling time. It also records how long
a message waits between its dispatch and the start of its handler.
These counters live in the backend's memory and build up from the
moment the process starts, so they always cover everything that
happened since the last release, with no extra infrastructure to run.

The backend ships with an operator dashboard that shows these numbers
live, as charts for the whole system and as a table per message type,
next to the request traces and the logs. The dashboard is not exposed
on the Internet: the reverse proxy only forwards the API and webhook
paths, so an operator opens it through an SSH tunnel to the host and
signs in as a system administrator.
Figure~\ref{fig:ui-comby-metrics} shows it running against the pilot.

\uishot[The runtime metrics dashboard]{ui-comby-metrics}
  {NOT the demo tenant: the backend operator dashboard
   (\texttt{/admin/} on the backend itself, via an SSH tunnel to the
   pilot host), Metrics area, Overview tab --- the three live charts
   (number per second, average processing times, average latencies)
   and the per-type entries table visible.}
  {The runtime metrics dashboard of the backend}

The numbers below were taken from this dashboard after the pilot had
run untouched for a little over a week. In that time the backend
handled 5{,}672 messages: 3{,}046 queries of 39 kinds, 2{,}583
commands of 18 kinds, and 43 domain events of 16 kinds. The mix shows
where the platform spends its time. All but 22 of the commands came
from the scheduler, whose hourly deadline, obligation and report
checks run once per tenant, signed in or not. What users trigger
directly is almost entirely reads. Table~\ref{tab:runtime-perf} picks
out representative operations.

The middle chart of the figure sums it up: queries stay near one
millisecond while commands sit around a hundred. In detail, the
3{,}046 queries averaged 1.3~ms of processing, the heaviest list
query 31~ms, and the slowest single query of the whole week took
52~ms. That is a tenth of the 500~ms search budget fixed in
Section~\ref{sec:nfr-perf}, before the network and the browser add
their part. The heavier work runs where nobody is waiting for it. The
scheduled checks average between 32 and 153~ms, with a worst case
just over one second, and the slowest events, the invitation and
approval notifications at about half a second, are e-mails sent
through the external provider after the user's request has already
returned. The one visible exception is sign-in, at about 184~ms; that
is the cost of checking the password, and it is intentional. The
dispatch layer itself is cheap: on average a command waits 0.3~ms
between its dispatch and the start of its handler.

Reliability over the same week: no message failed, and the 4
rejections were correct behaviour, not bugs. They were list requests refused by the access rules. A
quiet pilot says nothing about heavy load, which stays the job of the
performance tests, but it does replace the response-time assumptions
with measured values for every message type the platform uses.

\section*{Conclusion}
% intent: Close the walkthrough and the realisation as a whole, then bridge to
% the general conclusion. Per the report-wide rule, the conclusion may
% reference the NEXT chapter only -- here the Conclusion and Perspectives.
This chapter showed the delivered platform rather than its construction:
the sign-in that admits a user, the registry and the audit trail behind
every record, the configuration that fits the product to an
organisation, the approvals, deadlines and obligations it then watches
on that organisation's behalf, the suggestions and the signature
requests raised on a linked document, the reports and dashboards fed by
all of it, the interface in 2 languages with its documentation shipped
alongside, and the operator's own administration surface. The closing
measurements complete the picture from the other end, replacing the
platform's response-time assumptions with values recorded for every
message type it dispatches.

With the platform realised across 3 phases and shown here as it runs,
the contribution of this report is complete. The general conclusion that
follows recaps that contribution and sets out the perspectives for the
evolution of the event-sourced system beneath the platform.
