\section*{Introduction}
% intent: Frame the chapter as the realisation of the designed architecture
% across the full stack, consolidating Phases 0-2 by engineering theme rather
% than by phase. State the deliverable: a live pilot at clmpilot.com covering
% the contract lifecycle plus the enterprise capabilities of
% Section~\ref{sec:fr-enterprise}. Name the organising principle: each section
% is a recurring pattern that spans the stack, illustrated by the realised
% domains, never a per-tier or per-phase tour. Per the report-wide rule, the
% chapter intro must not reference other chapters.
This chapter presents the CLMPilot platform as it was built and
shipped. The result is a multi-tenant pilot, live in production at
\url{https://clmpilot.com}, that covers the full contract lifecycle and
extends it with an enterprise tier of capabilities:
intelligence-assisted extraction, electronic signature, per-tenant custom
fields, obligation tracking and advanced reporting. Each
section of the chapter follows one engineering theme across the whole
stack and uses the realised domains to illustrate it, starting from the
foundations and the delivery process, through the backend dispatch model,
the contract domain, the workflow and temporal automation, the
intelligence and signature subsystems, the web application, and identity
and tenancy in production, through the deployment and release operations
that keep the pilot running, down to the performance measured on the
pilot's own production traffic.

\section{Engineering foundations and the delivery process}
\label{sec:found}
% intent: Phase 0 as a set of decisions, not setup. The four-repository split
% by concern and release cadence; protected main/develop with feature->develop
% ->main promotion; the CI gate (lint/test/build/image push) and what each
% guards; conventional commits and per-repo semver for trivial rollbacks; the
% roadmap as the single source of truth; local dev mirroring production.
% Cite [[feedback-git-workflow]]; push YAML/commands to Appendix.
% figure: package/component diagram -- the four repositories and what each owns.
% (The project-timeline Gantt lives in Ch I Methodology, per supervisor
% feedback; Figure~\ref{fig:gantt} references resolve there.)

Phase~0 produced little product code, but it fixed the decisions every
later phase relied on. The first of them was to split the codebase into 4
repositories, each owning one concern and one release cadence;
Figure~\ref{fig:repos} shows what each repository owns in the realised
platform. The backend repository carries the Go service and its domain
contexts. The frontend repository carries the single-page
application, and the intelligence repository the Python extraction
service. The fourth, the deployment repository, holds the operational
stack itself: the Compose files, the reverse-proxy and service-unit
configuration, the release and backup scripts, and the runbooks that
explain how to operate them.

\begin{figure}[H]\centering
  \IfFileExists{Chapter4/figures/repos.pdf}
    {\includegraphics[width=0.9\linewidth]{repos}}
    {\fbox{\parbox{0.7\linewidth}{\centering\vspace{2em}
      \textit{Diagram to be rendered from} \texttt{figures/repos.puml}\vspace{2em}}}}
  \caption{The 4 repositories by concern}
  \label{fig:repos}
\end{figure}

The split is by concern, not by microservice: there is
one backend, not many. Each repository keeps its own toolchain and its
own release pace, so the frontend can ship without rebuilding the
backend, and a broken intelligence build never blocks a release. Each
also carries a small CI pipeline that runs in minutes. The price is that
a cross-cutting change, a new API field for instance, touches 2
repositories at once. We accepted that cost because the OpenAPI contract
makes the seam explicit: the client is regenerated from the
specification, and a build step keeps the 2 sides in sync.

Every repository follows the same branching rules. Day-to-day work
happens on short-lived feature branches merged into \texttt{develop}
through a reviewed pull request, and \texttt{main} receives merges only
from \texttt{develop}, one per release. This keeps \texttt{main}
deployable at all times, and it gives each release a diff of its own
that can be reviewed. Commit messages follow the conventional format and
name the roadmap item behind the change (Section~\ref{sec:methodology}).
Each repository is versioned independently under semantic versioning, so
rolling back a defective release means re-pinning a single version
number.

Continuous integration guards both branches in all 4 repositories, and
each pipeline is specific to what it protects. The backend pipeline
lints the Go code and runs the test suites against disposable
PostgreSQL, Redis and NATS containers~\cite{PostgreSQL,NATS}. The
frontend pipeline lints, runs the unit suite and builds the production
bundle; the intelligence pipeline runs its own linter and tests; the
deployment pipeline validates the Compose files and shell scripts it
ships. The 3 application pipelines end by building the repository's
Docker image and publishing it to the container registry the production
host pulls from, tagged with the commit, the branch and the release
version (Section~\ref{sec:deployment-ops}). Dependency updates arrive as
weekly automated pull requests and pass the same gate. The pipeline and
stack definitions are configuration; they are reproduced in
Appendix~A.3.

2 further foundations complete the delivery process. The local
development environment reproduces the production backing services
(PostgreSQL, Redis, NATS and MinIO, plus a local mail catcher) in a
Compose file of its own, brought up by an idempotent setup script, so
code is developed against the same services it will run on. And scope
was tracked in one place throughout: a versioned Markdown roadmap, from
which a progress tracker is regenerated automatically at phase, section
and task granularity (Section~\ref{sec:methodology}). Under this process
the 4 repositories accumulated more than 40 tagged releases over the
internship, each traceable from its version number back through the
release pull request to the roadmap items it delivered.

\section{Backend service architecture on comby}
\label{sec:backend-comby}
% intent: A single Go service hosting the comby kernel plus the domain modules;
% the registration/bootstrap order that command dispatch depends on
% ([[feedback-v3-post-facade-command-dispatch-broken]]); REST handlers as a
% thin shell translating HTTP into commands/queries and back, no business logic
% in handlers; the command path vs the query path; the command-vs-query
% authorisation asymmetry and its operational consequence
% ([[feedback-comby-command-auth-curl-gap]], detail to Appendix).
% figure: sequence diagram -- a command path and a query path, side by side.

The backend is a single Go process. At start-up it constructs the comby
facade and connects the backing services (the PostgreSQL event and
command stores, the Redis cache, the MinIO object store and the NATS
broker). It then registers the framework's default domains (tenant,
account, identity, group, invitation, asset and webhook), registers
CLMPilot's own contexts after them, and finally restores its state by
replaying the event log into the in-memory projections. Only then does
it serve requests. The comby layering of Section~\ref{sec:comby-role} is
visible in the code layout: the domain packages hold aggregates,
commands, events, read models and reactors, while dispatch, persistence,
tenancy and authentication all belong to the framework.

The boot sequence is ordered, and the order carries rules the
realisation had to respect. A command can be dispatched only once its
domain's handlers are registered; a boot-time action placed after the
facade exists but before registration completes simply fails, because
nothing routes the command yet. The platform's 2 seeding actions
therefore hook into fixed points of the sequence. Administrator seeding
(Section~\ref{sec:iam-practice}) runs inside domain registration, right
after the framework defaults are in place. Demo-data seeding runs only
after state restoration, because it depends on reactors, and reactors
begin processing live events once the projections are restored. We found
the first rule by hitting the failure; the second follows from the
framework's restore semantics. Both are now conventions of the codebase.

HTTP enters through a thin REST layer. comby generates handlers and an
OpenAPI document for every registered default, and CLMPilot's own routes
follow the same discipline: a handler validates the request's syntax,
translates it into a command or a query, dispatches it, and translates
the result back into a response. No handler contains a business rule.
Every rule lives in an aggregate or a command handler, where the event
log records its outcome. The exported specification counted +133
endpoints when the backend was first containerised and grew with each
later context; the frontend consumes it through a generated, type-safe
client (Section~\ref{sec:webapp}).

Figure~\ref{fig:backend-paths} shows the 2 request paths side by side,
as they are realised. A command (here, updating a contract) passes the
authorisation stage, reaches the aggregate, is validated against the
current state, and appends an event; the response returns once the event
is durable. A query (listing contracts) passes the same authorisation
stage, then reads a projection and writes nothing. Most views are served
by the framework's generic per-aggregate projection, which covers
retrieval and listing without custom code. Where a view has its own
access pattern, we built a dedicated read model: expiring contracts
sorted by end date, portfolio volume rolled up by quarter, department or
type at query time, and a case-insensitive search over the free-form
fields.

\begin{figure}[H]\centering
  \IfFileExists{Chapter4/figures/backend-paths.pdf}
    {\includegraphics[width=0.95\linewidth]{backend-paths}}
    {\fbox{\parbox{0.7\linewidth}{\centering\vspace{2em}
      \textit{Diagram to be rendered from} \texttt{figures/backend-paths.puml}\vspace{2em}}}}
  \caption{The realised command path and query path, side by side}
  \label{fig:backend-paths}
\end{figure}

Authorisation is attached to dispatch, and only to dispatch
(Section~\ref{sec:security-pipeline}); we learned the practical weight
of this during operations. Every command and every query is checked
against the caller's permissions when the bus routes it, so an endpoint
that read a store directly, without dispatching, would silently bypass
the check. The convention in the codebase is therefore to route reads
through dispatch even where a handler could reach a store directly. The
audit-export download of Section~\ref{sec:contract-domain} dispatches
the contract-retrieve query before serving a single byte for exactly
this reason, and the few endpoints that remain unauthenticated (the
inbound signature webhook, the OAuth callback) verify their callers by
other means. The same property produces an asymmetry between the 2
paths: a session that satisfies the query path can still be refused on
the command path. This is why administrative data corrections against
production are written as small system-dispatched routines executed at
boot, not as hand-issued API calls. The framework's command, query and
event catalogue, including the system-dispatch convention, is summarised
in Appendix~A.2.

\section{The contract domain and its lifecycle}
\label{sec:contract-domain}
% intent: Realisation of the Contract aggregate (metadata, status state machine,
% per-tenant custom fields) and of DocumentLink as the integration boundary
% turned domain object -- one aggregate, provider adapters for Google Drive,
% SharePoint and URL, reference-not-content enforced at this seam. The audit
% trail is anchored on Contract by construction.
% figure: class diagram -- the realised Contract + DocumentLink model with events.

The heart of the platform is the Contract aggregate: it realises the
contract registry that the functional requirements of
Section~\ref{sec:functional-requirements} place at the core of the
product. The aggregate carries the business metadata (counterparty, category and department,
value and currency, start and end dates, renewal terms) and a status
that moves only along the transitions of the state machine designed in
Section~\ref{sec:behavioural-views}: a draft becomes active, an active
contract may pass through expiring to expired, and an active or expiring
contract can be terminated early. The aggregate exposes 7 intentions
(register, update, terminate, archive, soft-delete, restore, and request
an audit export), and each guards its own preconditions. An update is
expressed as a set of patched fields, so the emitted event records
exactly what changed. Deletion is a flag rather than a removal, since
the immutability requirement of Section~\ref{sec:nfr-audit} forbids
destroying history. And a registration is only accepted after the
command handler has checked that the contract number is unique within
the tenant. Figure~\ref{fig:ui-contract-list} shows this registry as
the demo tenant's users see it.

\uishot[The contract registry]{ui-contract-list}
  {the contract registry with the filter bar and the free-text search
   active (e.g.\ filtered to one department).}
  {The contract registry: filterable listing backed by the
   case-insensitive search projection of
   Section~\ref{sec:backend-comby}.}

Every state change is an event appended to the contract's stream, so the
audit trail demanded by the compliance drivers exists by construction.
The platform exposes it in 3 forms. The application renders the raw
event list of a contract in its audit-log view, with the actor,
timestamp and payload of each entry. A reactor produces an exportable
report asynchronously, by replaying the contract's events into a tabular
file kept in the object store. And a download endpoint serves that file
after first dispatching the contract-retrieve query, so the export
inherits exactly the access control of the record it describes.
Figure~\ref{fig:ui-audit-trail} shows the first of the 3 forms on a
contract of the demo tenant.

\uishot[The audit-log view of a contract]{ui-audit-trail}
  {a contract's audit-log tab showing the event list with actor,
   timestamp and payload of each entry.}
  {The audit-log view of a contract: the raw event stream rendered
   with actor, timestamp and payload.}

Phase~2 extended the aggregate with per-tenant custom fields without
touching its core. A separate \texttt{CustomFieldDefinition} aggregate
lets each tenant's administrator define typed fields (text, number,
date, selection and boolean). A definition's key and type are immutable
after creation, because changing either would orphan or mistype the
values already recorded on contracts. The contract stores its custom
values as typed values with a canonical string encoding, chosen so that
replaying old events stays deterministic; the events also kept their
earlier plain-string form alongside the typed one, so history recorded
before the change replays losslessly. Validation crosses the 2 contexts.
The Contract command handlers accept an injected validator that checks
each value against the tenant's definitions: required fields are
present, values parse for their type, selections stay among the allowed
options. Values whose definitions have since been deleted are ignored,
so re-saving an old record never fails on removed configuration.
Figure~\ref{fig:ui-contract-form-custom-fields} shows the result on the
contract form: one typed widget per definition.

\uishot[The contract form with custom fields]{ui-contract-form-custom-fields}
  {the contract form of the demo tenant, scrolled to the
   tenant-defined custom fields so the data-driven widgets are
   visible.}
  {The contract form: fixed fields followed by the tenant's typed
   custom fields, one widget per definition.}

\texttt{DocumentLink} realises the integration boundary as a domain
object, as designed in Section~\ref{sec:aggregate-responsibilities}. One
aggregate serves all providers. Linking records a typed reference
(provider, external identifier, file name and MIME type) and overlays
metadata fetched from the provider at link time; unlinking and metadata
refresh complete its 3 intentions. The provider-specific work stays in
adapters behind a single \texttt{DocumentStore} interface: one for
Google~Drive, one for SharePoint through the Microsoft~Graph API, and a
pass-through for arbitrary URLs. The adapters authenticate with
per-tenant OAuth tokens held encrypted in the object store, only tenant
administrators may run the connect flow, and Appendix~A.4 walks through
the operator-facing setup for each provider. The integration-first rule
(a reference, never the contents) is enforced at this seam: no type in
the domain model can hold document bytes, so the claim that the platform
does not ingest customer documents can be checked in the model itself.
Figure~\ref{fig:contract-domain} draws the realised model, with the 2
aggregates, the definitions the contract validates against, the adapter
family behind the storage interface, and the events each aggregate
emits.

\section{Workflow and temporal automation}
\label{sec:workflow-temporal}
% intent: The three workflow/time contexts -- Approval (ordered multi-step
% review), Deadline (auto-created cancellation/renewal/expiry markers and
% reminders) and Obligation (post-signature, recurring) -- shown through the
% reactor pattern (a domain event derives a follow-up command, e.g. contract
% registered -> deadlines created) and the in-process cron scheduler that
% drives time-based checks. Idempotency by design, not by hope.
% figure: sequence diagram -- contract registration fires the deadline-creation
% reactor; or activity diagram for obligation recurrence.

3 contexts give the platform its behaviour over time. Approval is the
ordered review a contract passes before activation; Deadline covers the
temporal markers the platform watches on the contract's behalf;
Obligation covers the recurring commitments a signed contract creates.
All 3 are built from the same 2 mechanisms: reactors, which turn one
domain's event into another domain's command, and an in-process
scheduler, which turns the passage of time into commands on a fixed
calendar and so realises the system-clock actor of
Section~\ref{sec:actors}.

The approval workflow is an aggregate of ordered steps, each addressed
to a designated approver. Steps complete strictly in order, only the
designated approver may act on a step, and a single rejection moves the
whole workflow to rejected, matching the rules of
Table~\ref{tab:uc-approval-workflow}. Completion is recorded in 2
stages: each step completion is its own event, and a separate
finalisation event closes the workflow. The separation exists for the
reactor that watches the chain. When the last step completes, that
reactor dispatches the finalisation and then the contract update that
flips the target contract to active, which closes the draft-to-active
loop of Section~\ref{sec:behavioural-views}. A second reactor owns every
notification email the workflow sends. We kept state transitions and
side effects apart on purpose: a mail failure can never interfere with
the workflow's state, and each reactor fails on its own.
Figure~\ref{fig:ui-approval-inbox} shows the approver's side of this
workflow: the inbox of steps awaiting their designated approver.

\uishot[The approval inbox]{ui-approval-inbox}
  {the approval inbox of a user with at least one pending step; one
   workflow expanded to show the ordered steps.}
  {The approval inbox: ordered steps, each awaiting its designated
   approver.}

Most deadlines are created by automation rather than by hand.
Figure~\ref{fig:deadline-automation} follows the realised chain. A
cross-domain reactor listens for contract registration and derives up to
3 deadlines from the record itself: expiry at the end date, the
cancellation window at the end date minus the notice period (when that
window still lies ahead), and renewal when the contract auto-renews.
Each deadline carries reminder markers at 90, 60 and 30~days. In
Phase~2 the same reactor gained a second trigger: when the intelligence
pipeline extracts dates from a linked document
(Section~\ref{sec:intel-esign}), the resulting contract update seeds the
corresponding deadlines if they do not exist yet. A deadline the user
has edited is never touched.

\begin{figure}[H]\centering
  \IfFileExists{Chapter4/figures/deadline-automation.pdf}
    {\includegraphics[width=0.95\linewidth]{deadline-automation}}
    {\fbox{\parbox{0.7\linewidth}{\centering\vspace{2em}
      \textit{Diagram to be rendered from} \texttt{figures/deadline-automation.puml}\vspace{2em}}}}
  \caption{Temporal automation in the Deadline context}
  \label{fig:deadline-automation}
\end{figure}

Time enters through the scheduler, an in-process cron runner with
UTC-anchored jobs. An hourly job dispatches a batch command that
promotes every due reminder marker; a nightly job flips overdue
deadlines to missed. The batch commands are dispatched once per tenant,
so a failure in one tenant's batch cannot halt the others, and every job
logs its tenant count and duration. Reminder mail is opt-in per user:
before sending, the reminder reactors consult a per-identity preference,
and its absence means no mail. Later phases reused the pattern
unchanged. Obligation checks run on the same scheduler at offset minutes
so the batches do not contend; scheduled report exports run hourly
against each configuration's next-run date (Section~\ref{sec:webapp});
and a reconciliation job polls the signature provider for requests whose
webhooks were missed (Section~\ref{sec:intel-esign}). What this
automation produces for the user is the deadline view of
Figure~\ref{fig:ui-deadline-timeline}: the upcoming markers with their
reminder horizon.

\uishot[The deadline view]{ui-deadline-timeline}
  {the deadline view with upcoming deadlines and reminder markers (90,
   60, 30 days) visible.}
  {The deadline view: automation-created markers with their reminder
   horizon.}

Obligations, added in Phase~2, reuse the deadline mechanics but model a
different thing: a deadline is a date the platform watches, while an
obligation is a task a person owns and completes. Users create
obligations themselves; nothing derives them from contract fields. Their
reminder markers sit at 14, 7 and 1~days, the shorter horizon of
operational tasks, and their lifecycle ends in completed or missed. There
is no re-opening; a fresh occurrence is created instead. Recurrence is a
third reactor: completing a recurring obligation emits an event, and the
reactor spawns the next occurrence from it. The next due date is
computed by calendar arithmetic anchored to the original one (a monthly
task due on the 15th stays on the 15th) and rolled forward past the
present, so completing a task late never schedules an occurrence that is
already overdue. Figure~\ref{fig:ui-obligations} shows the obligation
view with a recurring commitment and its occurrences.

\uishot[Obligation tracking]{ui-obligations}
  {the obligation view with a recurring obligation and its
   completed/upcoming occurrences.}
  {Obligation tracking: person-owned recurring tasks with the shorter
   14/7/1-day reminder horizon.}

Idempotency in these contexts is a designed property, checked case by
case. Every reactor overrides its restore behaviour to skip replayed
events, so a restart, which replays the whole log to rebuild the
projections, re-sends no email and re-creates no record. And where
automation and users can race, the aggregate arbitrates: a reminder
event cannot overwrite an acknowledgement that arrived ahead of the
scheduler.

\section{Document intelligence and electronic signature}
\label{sec:intel-esign}
% intent: The two most novel Phase-2 subsystems. The stateless intelligence
% service (metadata extraction, classification, clause detection) behind an
% LLM gateway, with an evaluation harness as a design artefact; the enrichment
% reactor that folds AI suggestions onto a contract with accept/edit/undo, only
% filling empty fields. Electronic signature via DocuSeal: envelope dispatch,
% webhook reception as a domain-event source, signed PDF linked back as a
% DocumentLink, draft->active transition. Note scanned-PDF/OCR limit
% ([[project-pdf-clause-detection]]); cite [[project-smtp-provider]] for mail.
% figure: sequence diagram -- document linked -> extraction pipeline -> contract
% patched; component view of the e-signature webhook flow.

The 2 most substantial subsystems of the enterprise tier are built
around the linked document: the intelligence service reads it, and the
signature integration carries it through signing. Both were specified as
requirements in Section~\ref{sec:fr-enterprise}; this section presents
how they were built.

\subsection{Document intelligence}
\label{sec:doc-intel}

The intelligence service is a stateless Python service behind the
\texttt{IntelligenceClient} interface named in the architecture's
component view (Chapter~\ref{chap:arch}). It offers 3 operations
(metadata extraction, contract-type classification and clause
detection), each implemented as a prompt sent to a managed
large-language-model API~\cite{AnthropicClaude} behind a small internal
gateway. The service parses DOCX,
plain-text, Markdown and text-layer PDF documents itself, and passes a
PDF to the model as a document input only when it finds no text layer.
A language heuristic separates German from English, so German
legal-entity forms are preserved verbatim in extracted names.

Clause detection carries the subsystem's strictest design rule: every
detected clause must quote its source verbatim, and a clause whose
quoted snippet is not a substring of the document text is discarded.
This makes a hallucinated quotation structurally impossible. The same
guard also fixes the subsystem's limit. A scanned PDF has no text layer
to check quotations against, so clause detection on scans stays out of
scope until an optical-character-recognition step is added; extraction,
which does not quote, still works on scans through the model's vision
input.

The subsystem's quality is measured continuously. An evaluation harness
of 20 hand-labelled fixtures (plain-text and DOCX documents, 13 English
and 7 German, covering every contract type) runs in the integration
pipeline and scores each extracted field against its label. The baseline
stands at 158 of 160 fields correct (98.8\,\%). The harness paid for
itself during development, when a prompt revision raised
counterparty-name accuracy from 80\,\% to 90\,\% and the regression risk
was visible before release.

On the backend, an enrichment reactor connects this pipeline to the
contract. Figure~\ref{fig:enrichment-flow} follows the scenario. Once a
document is linked, the reactor downloads its bytes through the same
storage adapters as the link itself (capped at 50~MiB), calls extraction
and clause detection, and applies the results to the contract. Only
fields the user has left empty are filled; a human-entered value is
never overwritten. The call runs detached from the linking request,
under a 5-minute ceiling and a panic guard, which brought the latency of
the link operation from over 6 seconds to under 1. The suggestions
arrive on the record moments later, and the user reviews them field by
field (accept, edit or undo) in the interface of
Section~\ref{sec:webapp}. Re-linking the same document is treated as a
synchronisation and refreshes every extractable field.

\subsection{Electronic signature}
\label{sec:esign}

Electronic signature sits behind a provider-agnostic
\texttt{ESignatureProvider} interface, with the same discipline as
document storage: the domain model never names a vendor. The first
adapter targets DocuSeal~\cite{DocuSeal}, selected on 4 grounds. It can
be self-hosted under an open-source licence, which keeps signed
documents on the platform's own infrastructure. The simple electronic
signature it produces has legal effect for ordinary business contracts
under Article~25 of the eIDAS regulation~\cite{eIDAS}. It offers the
REST-and-webhook integration the reactor pattern needs. And it leaves an
upgrade path towards qualified signatures for the contract classes that
demand them.

The signature workflow is its own aggregate, modelled on Approval. A
request holds ordered signers, and events record dispatch, each signer's
completion or refusal, overall completion and voiding. Sending validates
that the contract is in a signable state, pulls the primary linked
document's bytes through the storage adapters, and hands them to the
provider. The tenant, contract and request identifiers are stamped into
the provider's submission metadata, so whatever comes back can be
routed.

Figure~\ref{fig:esign-webhook} shows the return path. Signing progress
arrives as webhooks on a public endpoint, which verifies the provider's
signature before parsing anything, reads the routing identifiers back
out of the submission metadata, and translates the provider's event into
a status-application command dispatched with system authority. Applying
status is idempotent: a duplicate or out-of-order delivery is compared
against the aggregate's current state and ignored when stale. Completion
then triggers a reactor in the contract domain, which marks the
contract's signature status, flips a draft contract to active, downloads
the signed PDF from the provider and links it back to the contract as an
ordinary \texttt{DocumentLink}, so the executed document enters the same
audit trail as everything else. Webhooks can be lost, so the scheduled
reconciliation job of Section~\ref{sec:workflow-temporal} polls the
provider for requests stuck in a sent state past a threshold. We
validated the whole path end to end against DocuSeal's hosted sandbox;
in production the integration stays inactive until an operator
configures a provider key.

The web application is a single-page application built with Vue~3 and

stores, composables and utilities that the unit suite (198 tests at the

\section{Identity, access control and multi-tenancy in practice}
\label{sec:iam-practice}
% intent: The realised identity model from the comby defaults (tenant, account,
% identity, group, permission), the five RBAC role groups, email-OTP MFA, and
% the authentication user journey (login, self-serve registration with a
% pre-issued login token [[reference-comby-register-confirm-token]], password
% reset). Tenant isolation in practice -- the archived-tenant middleware and the
% seeded system-administrator cross-tenant interface. RBAC drives both backend
% authorisation and frontend affordances ([[feedback-skipauth-tests-miss-rbac]]).
% figure: sequence diagram -- the authentication journey across the full stack.

The identity model in production is the comby default model of
Section~\ref{sec:identity-model}, used without modification: tenants for
customer organisations, accounts for people, identities binding an
account into a tenant, groups as roles, and permissions as the right to
dispatch a given command or query. What CLMPilot adds is the vocabulary
on top of it: a typed catalogue of permission constants covering every
domain, and 5 role groups (administrator, legal, finance, manager and
viewer) whose permission bundles are seeded into every new tenant by a
reactor listening for tenant creation, so a freshly provisioned
organisation starts with a working role set. Tests guard the catalogue's
invariants and hold the viewer and finance roles to read-only bundles,
with no command permission at all.

Figure~\ref{fig:auth-journey} follows a sign-in across the stack.
Authentication is 2-step: the credentials are checked first, then a
one-time code sent by email must be confirmed, after which the backend
issues the opaque session cookie and the companion identity cookie that
scopes every later request to a tenant
(Section~\ref{sec:security-pipeline}). The client mirrors the session's
lifetime and refreshes it shortly before expiry, so a working user is
never interrupted. Self-serve registration through an invitation follows
the same rails, with one refinement found in the framework's internals:
confirming a registration already returns a pre-issued login token,
which the client feeds straight into the login confirmation, so a new
user completes registration with exactly one code and lands
authenticated. A password-reset flow completes the account lifecycle.
The invitation page also inserts an explicit human click before any
state-changing step, because corporate mail scanners follow links and
would otherwise consume single-use invitation tokens.

Role-based access control is enforced at dispatch
(Section~\ref{sec:security-pipeline}), and the realisation taught us 2
rules about it. First, the permission string checked at dispatch is
derived from the command or query type itself, so the catalogue's
constants must match those derived names exactly. After a mismatched
constant silently produced a permission that no role could ever hold, a
regression test now derives every name by reflection and compares.
Second, integration tests that dispatch with system authority never
exercise the authorisation stage. That blind spot let 3
role-configuration defects stay invisible until the first ordinary
tenant hit the standard path, because the platform operators used until
then bypass the role check entirely. The countermeasure is an end-to-end
suite that authenticates as a real user against the running API, so
every permission a role needs is proven from the outside. The frontend
consumes the same vocabulary through a permission composable that hides
actions a role cannot perform; the backend remains authoritative.

Multi-tenancy in operation needs administration as much as isolation. A
reserved system tenant holds the platform's operators, seeded at boot
from configuration, so an administrator can be added or recovered
without touching the database. The operators work through a cross-tenant
administration area in the application itself, which provisions a
tenant, waits for its role groups to be seeded, and issues the first
administrator invitation. Decommissioning is archival. Archiving marks
the tenant, and a middleware on both dispatch paths refuses every
request scoped to an archived tenant unless the caller is a platform
operator; the client translates the refusal into an explicit
end-of-service screen. The archived state is therefore enforced at the
same chokepoint as every other rule, and the user interface only
reflects it. Figure~\ref{fig:ui-admin-tenants} shows the operators'
administration area on the pilot.

\section{Production deployment and release operations}
\label{sec:deployment-ops}
% intent: The operational realisation of Chapter II's topology. The single
% EU-hosted Hetzner Docker-Compose stack, host nginx + certbot TLS, loopback
% binding; backups with an off-host retention and a verified restore drill;
% observability posture (structured logs, Prometheus metrics emitted but not yet
% aggregated -- honest about the MVP; the in-process runtime measurements get
% their own closing section, sec:runtime-perf); the release
% process (develop->main,
% image build, tag bump, deploy.sh on the host) and the deploy.sh lockstep
% caveat with the bypass ([[feedback-deploy-script-lockstep-pain]], Appendix);
% the apex-domain choice ([[project-apex-domain]]); MVP availability/performance
% posture now that production traffic can be observed.
% figure: deployment diagram -- the realised production topology.

Production realises the topology of Section~\ref{sec:deployment-topology}
on a single EU-hosted virtual machine at Hetzner, a 4~GB instance sized
for the pilot. Figure~\ref{fig:production-topology} shows the
operational view. The 3 service images and the 4 backing stores run as
one Docker~Compose stack~\cite{DockerCompose} under a systemd unit, so
the stack survives a reboot. Every container binds to loopback, and the
only process facing the network is an nginx reverse proxy on the host,
which terminates TLS with certificates issued and renewed automatically
through Let's~Encrypt. Memory limits are set per container, and
PostgreSQL is tuned to the small host, which keeps the single-machine
footprint predictable under load.

\begin{figure}[H]\centering
  \IfFileExists{Chapter4/figures/production-topology.pdf}
    {\includegraphics[width=\linewidth]{production-topology}}
    {\fbox{\parbox{0.7\linewidth}{\centering\vspace{2em}
      \textit{Diagram to be rendered from} \texttt{figures/production-topology.puml}\vspace{2em}}}}
  \caption{The production topology}
  \label{fig:production-topology}
\end{figure}

The platform serves at the apex domain, \texttt{clmpilot.com}, with the
API under the same origin. That choice removes a class of complexity:
same-origin requests need no cross-origin configuration, cookies operate
under the strictest same-site policy, and one certificate covers the
whole product. An earlier subdomain plan was dropped, and its stale
references were cleaned out of the stack once the apex choice was final.

Backups follow the recovery objectives fixed with the non-functional
requirements (Chapter~\ref{chap:analysis}). A nightly database dump
leaves the host for object storage at a second provider, so the loss of
the machine cannot take the backups with it. We validated the procedure
with a full drill against production: back up, drop the databases,
restore, and let the backend rebuild every projection by replaying the
restored event log. The drill confirmed the recovery-point objective
(under 24 hours, one nightly backup) and beat the 4-hour recovery-time
objective by a wide margin; restore and replay completed in under a
minute at pilot volume. The replay step doubles as an integrity check of
the event-sourced design, since the read models are rebuilt from the
restored log alone: a successful drill proves the log is sufficient to
reconstruct the system.

Observability at pilot scale deliberately adds no external tooling. The
services emit structured logs, tagged by component, and these are the
primary diagnostic tool. The backend exposes metrics in Prometheus
format, but no aggregation stack runs on the host yet, a decision
consistent with the maintainability driver of
Section~\ref{sec:arch-drivers}. External monitoring covers what users
experience: an independent probe checks the public health endpoint
every 5 minutes and alerts by email, and the TLS configuration holds
the highest public rating. One detail forced a choice here: the
backend's minimal container image ships no shell, so container-level
health checks gave way to probes from outside the container. What the host does not aggregate, the backend still
measures in-process; that evidence closes the chapter in
Section~\ref{sec:runtime-perf}.

A release is a promotion, not a build performed on the host. Work
merges into \texttt{develop}; a release pull request promotes
\texttt{develop} to \texttt{main}; a semantic-version tag triggers the
pipeline that builds and publishes the image; and a deployment script on
the host pins the new versions in the environment, pulls the images,
restarts the stack and polls the health endpoint before reporting
success. Rollback is the same procedure with the previous version
numbers. The script carries one caveat we hit in practice: it pins all 3
service versions in lockstep, which keeps a full release reproducible
but makes a single-service hotfix awkward. Partial releases therefore
bypass the script and edit the pinned versions directly, and the
services were re-unified onto one version at the close of Phase~2 so
that the lockstep procedure and its rollback work again. The script and
the bypass are reproduced in Appendix~A.3.

With production traffic observable, the availability and performance
targets of Section~\ref{sec:nfr-perf} moved from assumptions to
measurements. Deploys complete in well under the recovery-time budget,
the uptime probe provides the availability record against which the MVP
target is checked, the runtime measurements of
Section~\ref{sec:runtime-perf} supply the server-side record behind
the response-time budgets, and the pilot's operational history (more than 40
releases, a single rolled-back deployment during a framework migration,
and no data loss) is the evidence those targets were set to collect.

The chapter closes with measurements from the running pilot. Since
every command, query and event goes through the same dispatch point,
the framework can count them all: how many succeeded, failed or were
rejected, how many arrive per second, and for each message type the
shortest, average and longest handling time. It also records how long
a message waits between its dispatch and the start of its handler.
These counters live in the backend's memory and build up from the
moment the process starts, so they always cover everything that
happened since the last release, with no extra infrastructure to run.

The backend ships with an operator dashboard that shows these numbers
live, as charts for the whole system and as a table per message type,
next to the request traces and the logs. The dashboard is not exposed
on the Internet: the reverse proxy only forwards the API and webhook
paths, so an operator opens it through an SSH tunnel to the host and
signs in as a system administrator.

The middle chart of the figure sums it up: queries stay near one
millisecond while commands sit around a hundred. In detail, the
3{,}046 queries averaged 1.3~ms of processing, the heaviest list
query 31~ms, and the slowest single query of the whole week took
52~ms. That is a tenth of the 500~ms search budget fixed in
Section~\ref{sec:nfr-perf}, before the network and the browser add

scheduled checks average between 32 and 153~ms, with a worst case
just over one second, and the slowest events, the invitation and
approval notifications at about half a second, are e-mails sent
through the external provider after the user's request has already
returned. The one visible exception is sign-in, at about 184~ms; that

dispatch layer itself is cheap: on average a command waits 0.3~ms
between its dispatch and the start of its handler.

rejections were correct behaviour, not bugs. They were list requests refused by the access rules. A
quiet pilot says nothing about heavy load, which stays the job of the
performance tests, but it does replace the response-time assumptions
with measured values for every message type the platform uses.
